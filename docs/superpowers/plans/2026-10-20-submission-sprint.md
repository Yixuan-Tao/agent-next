# 同机并行手机 Agent 提交冲刺计划

日期：2026-10-20。代码基线：`b242ee6`。本文件保留执行目标；实际进度见下方及 [提交演练记录](../../submission-demo.md)，未勾选项目尚未验收。

## 目标与时间假设

按剩余 1–2 天、单人配合 AI 编码、约 12–16 小时有效工作估算。交付目标是一条可重复的端到端链路：用户持续使用同一台设备的主屏，Agent 根据实时界面自主完成一个第三方 App 的多步任务；电脑同时显示后台实际画面，最终结果能在 App 中检查。题目允许只选一个任务，不以完整内部 Beta 为本次提交门槛。

复用现有 Android/Shizuku、私有 display、brain 和模型配置。优先使用已经有设备 smoke 的测试设备；README 和视频明确设备型号，平板记录不写成手机实测。冻结一个设备、App 版本和 commit 后再录制。

## 仅推进三个优化点

### 1. 打通无干扰执行与电脑端只读监看

当前阻塞：`PreviewActivity.onCreate()` 会暂停 Agent，`BlockingDeviceApi` 在 preview 激活时拒绝 Agent 输入；现有预览属于人工接管。设备状态文档还记录了启动后 shell 退出、首次动作前 `UNAVAILABLE`，不能把这些当作已解决。

- 修复当前设备上启动到首个动作之间的断连，依据 close 调用栈和服务退出日志定位原因；保留正常结束和停止时的资源释放。
- 增加只读监看通道，输出到电脑；不进入 `PreviewActivity`，不获取用户输入所有权。已有交互预览继续用于显式接管。
- 优先复用目标帧采集：串行调度设备调用，复制 PNG 后再发布，避免监看与执行竞争 observation/frame lease；电脑端显示帧序号、时间和失效状态。目标约 1–2 fps，先验证实际延迟和兼容性，不承诺该帧率已达成。监看缺帧须标明，不把旧帧标成直播。
- 人工交接只发通知；必须等用户主动选择接管才移动 target 到主屏。登录/CAPTCHA 不自动抢屏。

验收：用户在主屏连续中文输入和滚动时，Agent 仍执行；主屏 App 不切换、输入内容不丢失、键盘不关闭。电脑能看到执行过程，监看本身不暂停 Agent。

### 2. 收敛为一个根据观察决策的真实任务，并独立核验结果

优先候选：在夸克搜索用户指定主题，打开相关结果，停在正文并报告页面标题。例如“搜索西红柿炒鸡蛋的做法，打开一篇相关内容，告诉我标题”。先检查设备实际安装和页面可观察性；两小时可行性检查后冻结任务。

当前 QuarkWeatherPolicy 固定上海/明天、按步骤推进，FilesGuiPolicy 是固定组合流程；本次不能用这两条路径来证明自主决策。候选浏览器任务使用现有通用模型策略，依据每次新观察提出下一步。适配只帮助识别控件，不预排输入序列。

- 在计划确认时保存本次用户确认的搜索主题、目标页面和结束边界；结束后逐项核验，不从执行后的计划文本推导成功。
- 每步观察；加载仅有界等待，普通可关闭弹窗根据实际控件处理，节点变化后重新定位。最多一次局部恢复；修复前不调用当前会取候选计划首节点替换当前节点的全任务重规划逻辑。
- 风险分类读取实际命中的控件及页面内容，不能只信动作描述；密码、验证码、支付、发送、删除等超出本任务边界时停止并提示。
- 最后检查搜索主题匹配、实际打开的内容页及标题证据；证据不足为 `UNKNOWN/NEED_USER`，成功才报告 `DONE`。保留最终画面，让评审可人工复核；主题相关性仍有视觉模型局限，需在记录中说明。

验收：不同主题下均根据新页面做决策；从不同初始页面重跑；最终 App 页面与报告对应。至少完成三次连续自主运行，包括一次普通加载或非安全弹窗变化。记录全部尝试和人工介入，不把此小样本写成通用成功率。

### 3. 形成一次可复现的提交和答辩材料

- 连续录制 60–120 秒：同一画面可见用户操作主屏、电脑端后台画面，任务运行阶段不切断时间线；完成后展示 App 内的结果和报告。
- 固定 APK、源码 commit、设备/App/模型版本、提示词与脱敏日志。电脑只监看，不暗中替 Agent 点击或输入。
- README 增加这次实际验证的任务、视频链接、权限与复现步骤、已知失败；准备架构与取舍、失败分析、AI 协作方式各一段。仓库可私有，但须确保面试方有权限。

验收：另一位读者按 README 能启动同一任务；视频证明真实同时执行；结论与日志一致，失败和协助明确标记。

## 执行顺序与时间盒

| 顺序 | 时间预算 | 操作与可能修改的文件 | 结束检查 |
|---|---|---|---|
| T0 可行性检查 | 0–2 小时 | 选择设备；复核 `AgentRuntime` / Shizuku 退出日志；试通用浏览器路径；检查可取到的后台帧；修正 `BlockingDeviceApi` 新增 Android Log 导致的 host 编译回归 | 至少能启动真实 App、完成首个模型动作，主屏仍可输入；确认只读画面输出的可行方式 |
| T1 执行生命周期 | 约 2 小时 | `app/src/main/java/agent/next/app/AgentRuntime.java`、`AgentTaskService.java`、`MainActivity.java`；只修导致断连/提前清理的触发路径 | 用户离开 AgentNext 后，当前任务继续；结束/停止可释放资源 |
| T2 只读画面 | 约 2 小时 | `AgentRuntime.java`、`capability/src/main/java/agent/phone/capability/BlockingDeviceApi.java`；拟新增 `app/src/main/java/agent/next/app/DemoFramePublisher.java` 和 `tools/demo-viewer.py` | debug-only 输出、设备调用串行；PC 可观察且不会触发 preview 所有权；输出不提交个人画面 |
| T3 受控任务路径 | 约 2 小时 | `AgentRuntime.java`、`brain/src/main/java/agent/next/brain/session/PromptSessionPolicyFactory.java`、`app/src/main/java/agent/next/app/skill/RiskGuardPolicy.java` | 通用模型选动作；可按页面加载/普通弹窗改变动作；禁用有缺陷的全任务重规划 |
| T4 结果与风险 | 约 2 小时 | `brain/src/main/java/agent/next/brain/action/ActionGrounder.java`、`GuiRiskClassifier.java`；拟新增 `app/src/main/java/agent/next/app/skill/BrowserResultVerifier.java`；接线 `AgentRuntime.java` | 实际危险控件不能用中性描述绕过；本次已确认的条件逐项核验；旧结果不算完成 |
| T5 回归与演练 | 约 2 小时 | 新增上述风险/结果边界回归至现有 brain 测试；保存脱敏运行记录 | host 通过、APK 可构建；三次自主运行；输入与滚动并发、停止、一次失败不误报 |
| T6 录制与提交 | 约 2 小时 | `README.md`；拟新增 `docs/submission-demo.md`（设备/版本/步骤/运行结论/材料链接） | 1–2 分钟同步演示；源码与 APK 一致；面试方仓库访问权限确认 |

上表合计最多约 14 小时，另留 2 小时处理阻塞，总预算上限约 16 小时；T0 若提前通过，节省时间留给录制和失败重跑。每段到点后检查是否达到结束条件，未达到时先削减后续范围，不继续增加功能。

### 两个停止扩展的检查点

1. **第 2 小时**：若仍不能执行首个 GUI 动作，或后台采集必然干扰主屏，就集中修该阻塞，不进入新技能开发。若只能提交未完成结果，保留尝试、日志和根因，明确尚未满足核心要求。
2. **录制前至少留 3 小时**：冻结功能，只修阻塞既定任务的问题并准备材料。无法稳定打开内容页时，可在重新确定并确认任务后收敛为“搜索并停留在指定结果页”；须从一开始按这个任务录制和核验，不能把未完成的原任务重命名成完成。
